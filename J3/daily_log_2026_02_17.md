# Daily Log: 2026-02-17
## Analyzing and Improving Pipeline Robustness

### 1. Missing Value Strategy Analysis
*   **Context**: The previous pipeline used `fillna(0)` blindly.
*   **Action**: 
    *   Created `J3/compare_nan_strategies.py` to benchmark 3 strategies: `fillna(0)`, `Mean Imputation`, and `Native LightGBM` (leaving NaNs as is).
    *   **Result**: Native LightGBM handling performed best (~0.5318 Accuracy vs 0.5306 for fillna0).
*   **Missingness Mechanism**:
    *   Created `J3/missingness_analysis.ipynb`.
    *   Found high missingness in Volume features (~73%).
    *   **Key Insight**: Missingness had extremely low correlation with the Target (< 0.014), suggesting MCAR/MAR (non-informative).
*   **Decision**: Removed all `fillna(0)` calls from `J3/full_pipeline_run.py` and `J3/run_pipeline.py`.

### 2. Adversarial Validation (Drift Detection)
*   **Goal**: Reduce the gap between CV (Cross-Validation) and LB (Leaderboard) scores.
*   **Implementation**:
    *   Added `check_drift` method to `FeatureEvaluator` class in `pipeline/feature_selection.py`.
    *   Methodology: Train a LightGBM classifier to distinguish Train rows from Test rows. High AUC = High Drift.
    *   Integrated this check into both `J3/run_pipeline.py` (Sample) and `J3/full_pipeline_run.py` (Full).
*   **Technical Fixes**:
    *   Fixed a bug where `pd.concat` failed due to duplicate columns in feature generation (added deduplication steps).
    *   Fixed index alignment issues during drift check on sample data.

### 3. Full Pipeline Execution & Submission
*   **Execution**: Ran `J3/full_pipeline_run.py`.
    *   **Drift Result**: AUC of **0.6180**.
    *   **Threshold**: The cutoff was set at **0.70**.
    *   **Outcome**: No features were dropped because drift (0.618) < threshold (0.70).
*   **Validation**: 
    *   Optuna found best params (Accuracy ~0.562 CV).
    *   Submission file `submission_lgbm_optuna_binary.csv` generated.
*   **Leaderboard Result**:
    *   **Score**: 0.5085 (Very poor).
    *   **Analysis**: The drift of 0.618, while "moderate", was apparently enough to cause significant performance degradation on the test set. The model likely overfitted to the training distribution.

### 4. Next Steps (Proposed)
*   **Tighten Drift Controls**: Lower the Adversarial Validation threshold from `0.70` to **0.60** to force the removal of drifting features.
*   **Re-evaluate Missingness**: If native handling is too unstable, reconsider explicit imputation (e.g., Mean or KNN) to stabilize the feature space.
